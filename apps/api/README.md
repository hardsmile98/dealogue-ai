# api — Dealogue AI (backend)

NestJS 12 (ESM) + TypeORM + PostgreSQL. Авторизация по логину и паролю,
access-токен — JWT.

## Быстрый старт

```bash
docker compose up -d
```

```bash
cp .env.example .env && npm install --legacy-peer-deps && npm run migration:run && npm run start:dev
```

API поднимется на http://localhost:3000. Сид-миграция заводит пользователя
из `SEED_USER_LOGIN` / `SEED_USER_PASSWORD` (по умолчанию `demo` / `demo1234`).
Задать их нужно **до** первого `npm run migration:run`: уже применённая
миграция повторно не выполняется. Если опоздали — откатите сид, поправьте
`.env` и накатите заново, **именно в таком порядке**:

```bash
npm run migration:revert && npm run migration:run
```

Откат ищет пользователя по текущему `SEED_USER_LOGIN`, поэтому если логин
в `.env` уже изменён, откатывать нужно со старым значением:
`SEED_USER_LOGIN=прежний npm run migration:revert`.

## Эндпоинты

### `POST /auth/login`

```json
{ "login": "demo", "password": "demo1234" }
```

`200` →

```json
{
  "accessToken": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "user": { "id": "uuid", "login": "demo", "name": "Демо-пользователь" }
}
```

- `401` — неверная пара логин/пароль (одинаковый ответ и для чужого логина,
  и для неверного пароля).
- `400` — не прошла валидация тела (пустое поле, лишнее поле, перебор длины).

Логин нечувствителен к регистру и пробелам по краям: `"  DEMO  "` найдёт `demo`.

### `GET /auth/me`

Требует `Authorization: Bearer <accessToken>`. Отдаёт актуального пользователя,
`401` — если токена нет, он битый, истёк или пользователя уже удалили.

## Telegram

Подключение аккаунтов пользователей Telegram через MTProto на
[teleproto](https://www.npmjs.com/package/teleproto), отслеживание сообщений
и статистика по первым сообщениям диалогов. Все эндпоинты — под
`Authorization: Bearer`, аккаунты видны только их владельцу.

### Настройка

В `.env` (см. `.env.example`):

| Переменная                                                      | Что это                                                                                                                                                             |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `TELEGRAM_API_ID`, `TELEGRAM_API_HASH`                          | приложение с https://my.telegram.org/apps. Без них раздел выключен: `/telegram/*` отвечает 503                                                                      |
| `TELEGRAM_SESSION_SECRET`                                       | ключ AES-256-GCM для сессий в базе. Обязателен при включённом разделе; при потере все аккаунты придётся переподключить                                              |
| `TELEGRAM_MTPROXY`                                              | `host:port:secret[,host2:port2:secret2]` — MTProxy (из России Telegram напрямую недоступен). Несколько адресов перебираются по кругу, подключаемся к первому живому |
| `TELEGRAM_TIMEZONE`                                             | зона «дня» для статистики по умолчанию; фронтенд передаёт свою в `tz=`                                                                                              |
| `TELEGRAM_SYNC_DIALOGS_LIMIT`, `TELEGRAM_SYNC_MESSAGES_LIMIT`   | сколько личных диалогов и последних сообщений на диалог забирать при первом подключении                                                                             |
| `TELEGRAM_RESYNC_INTERVAL_SEC`, `TELEGRAM_RESYNC_DIALOGS_LIMIT` | периодическая досинхронизация: интервал и сколько свежих диалогов проверять                                                                                         |
| `TELEGRAM_LOGIN_ATTEMPT_TTL_SEC`                                | сколько живёт незавершённый вход                                                                                                                                    |

Секрет MTProxy — hex: `dd…` (random padding) или `ee…` + домен (fake-TLS).
Для таких секретов прокси принимает только транспорт padded intermediate
(тег `0xdddddddd`), а teleproto для MTProxy всегда шлёт abridged — прокси
молча рвёт соединение («NetSocket was closed» на первом же пакете). Поэтому
`client/mtproxy-padded-transport.ts` подменяет класс соединения на свой
`ConnectionTCPMTProxyPadded`; «голые» 16-байтовые секреты идут через abridged
как раньше.

### Эндпоинты (`/telegram/accounts`)

| Метод  | Путь                                                        | Что делает                                                                                     |
| ------ | ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| GET    | `/`                                                         | список аккаунтов с числом новых диалогов за сегодня                                            |
| POST   | `/send-code` `{ phone }`                                    | отправить код в Telegram → `{ attemptId, phone }`                                              |
| POST   | `/sign-in` `{ attemptId, code }`                            | ввести код → `{ status: 'connected', account }` или `{ status: 'password_required' }` при 2FA  |
| POST   | `/password` `{ attemptId, password }`                       | облачный пароль → `{ status: 'connected', account }`                                           |
| GET    | `/:id`                                                      | карточка аккаунта                                                                              |
| DELETE | `/:id`                                                      | завершить сессию в Telegram и удалить аккаунт с историей                                       |
| GET    | `/:id/stats?from=YYYY-MM-DD&to=YYYY-MM-DD&tz=Europe/Moscow` | первые входящие сообщения по дням и кодам, итоги и итоги за предыдущий период                  |
| GET    | `/:id/chats?cursor=&limit=100&search=&code=with\|without`   | страница личных диалогов (свежие первыми) → `{ items, nextCursor, total }`                     |
| GET    | `/:id/chats/:chatId`                                        | один диалог — для прямой ссылки на чат                                                         |
| GET    | `/:id/chats/:chatId/messages?cursor=&limit=50`              | страница переписки: свежие сообщения, по `nextCursor` — более старые → `{ items, nextCursor }` |
| POST   | `/:id/chats/:chatId/messages` `{ text }`                    | ответ клиенту от имени аккаунта                                                                |

**Переписка — тоже по курсору, от новых к старым.** Первая страница — самые
свежие сообщения, каждая следующая — всё, что строго раньше самого старого
сообщения предыдущей (ключ `sent_at, telegram_message_id`, индекс
`IDX_telegram_messages_chat_sent_id`). Внутри страницы сообщения идут по
возрастанию времени — веб просто склеивает страницы в обратном порядке.

**Список чатов — постраничный, по курсору.** Порядок — по последнему
сообщению (чаты без сообщений в конце), затем по id; `nextCursor` — ключ
сортировки последнего чата страницы, следующая страница начинается строго
после него. В отличие от OFFSET, чат, который поднялся наверх из-за нового
сообщения, не сдвигает остальные и не дублируется. Индекс
`IDX_telegram_chats_account_last_id` построен по тому же выражению, поэтому
любая страница читается прямо с места курсора. `search` ищет подстроку
(без учёта регистра) в имени, username, телефоне и тексте последнего
сообщения; `total` — сколько чатов подходит под фильтры.

Ошибки Telegram переводятся в понятные тексты (`lib/telegram-errors.ts`):
неверный код — 400, номер заблокирован — 403, `FLOOD_WAIT` — 429 с числом
минут, прокси недоступен — 503. При отправке сообщения: аккаунт не подключён
или его сессия отозвана — 503, собеседник заблокировал аккаунт — 403,
удалил свой аккаунт — 410, не резолвится — 409, Telegram не подтвердил
отправку за 30 с — 504 (сообщение могло уйти, повторять вслепую нельзя).

### Как это работает

**Вход.** `send-code` поднимает клиент через MTProxy, просит код и сохраняет
сессию (зашифрованную) вместе с `phoneCodeHash` в `telegram_login_attempts` —
ввод кода переживает перезапуск API. `sign-in` вызывает `auth.signIn`; на
`SESSION_PASSWORD_NEEDED` возвращает `password_required`, тогда `password`
делает SRP-проверку (`account.getPassword` + `auth.checkPassword`). После
успеха создаётся или обновляется строка `telegram_accounts` и клиент сразу
передаётся рантайму — второе соединение не открывается. Повторный вход по
номеру отвалившегося аккаунта переподключает его с сохранённой историей.

**Рантайм** (`runtime/telegram-runtime.service.ts`). Когда HTTP-сервер занял
порт, API поднимает по клиенту на каждый аккаунт со статусом `connected` /
`error` — в фоне, с разбегом в 0,7 с, но не дожидаясь друг друга: аккаунт за
мёртвым прокси не задерживает остальные. Второй экземпляр API на занятом
порту падает раньше и клиентов на те же сессии не поднимает. Рантайм отвечает только за жизненный цикл клиента
(подключение, сторож, повторы, статус). Апдейты принимает
`runtime/telegram-updates.service.ts`: входящие и исходящие сообщения личных
чатов сразу пишутся в базу, прочтение наших исходящих и «печатает…» идут в
шину. Если диалог ещё не известен, для него один раз забирается история —
иначе «первое сообщение» было бы определено неверно.

**Синхронизация** (`services/telegram-sync.service.ts`). Первичная: все
личные диалоги (без ботов, «Избранного» и удалённых), для каждого — последние
N сообщений и самое первое (по нему фиксируются `first_message_at`,
направление и код). Если последние N и есть вся история (типичный короткий
диалог с лидом), второй запрос за первым сообщением не делается.
Периодическая: раз в `TELEGRAM_RESYNC_INTERVAL_SEC` проверяются свежие
диалоги (их чаты читаются и заводятся одной пачкой) и догружается всё, что
новее последнего сохранённого id, — это страхует от пропущенных событий при
обрывах связи.

**Запись в базу** (`repositories/`). Весь SQL по таблицам Telegram — в трёх
репозиториях. Приём сообщения — три запроса: найти чат, вставить сообщения
одним `INSERT … SELECT FROM unnest(…) ON CONFLICT DO NOTHING RETURNING *`,
обновить агрегаты чата одним `UPDATE`. Счётчик, «последнее сообщение»,
граница прочитанного и статус аккаунта меняются выражениями от текущих
значений строки (`messages_count + n`, `GREATEST(…)`, `WHERE read_outbox_max_id < $2`),
а не перезаписью прочитанной ранее сущности, — событие и синхронизация одного
чата могут идти параллельно и не затирают друг друга.

**Стабильность.**

- teleproto сам переподключается при обрыве; если соединение всё же потеряно,
  рантайм пересоздаёт клиент с экспоненциальной паузой (15 с → 5 мин),
  перебирая прокси из списка.
- Короткие `FLOOD_WAIT` (до 30 с) библиотека пересиживает сама, длинные
  показываются в статусе аккаунта, следующий цикл повторит попытку.
- `AUTH_KEY_UNREGISTERED` / `SESSION_REVOKED` / `USER_DEACTIVATED` переводят
  аккаунт в `disconnected`, сессия стирается — в списке появляется кнопка
  «Переподключить». Коды сравниваются целиком: `INPUT_USER_DEACTIVATED`
  (аккаунт удалил собеседник) к потере сессии не относится.
- Запись сообщений идемпотентна (`ON CONFLICT DO NOTHING` по паре
  chat + telegram_message_id), гонка события и синхронизации безопасна.
- Фоновые задачи (таймеры, обработчики апдейтов, повторы) ловят свои ошибки
  (`common/async.ts` → `runDetached`): временно недоступная база пишется в
  лог и не роняет процесс вместе со всеми подключениями. Запасной
  обработчик `unhandledRejection` в `main.ts` делает то же для того, что
  всё-таки ускользнёт.
- На одну сессию — один клиент: повторный запуск аккаунта, пока он ещё
  подключается, ничего не делает, а подключение, которое закончилось после
  удаления аккаунта, выбрасывается.
- Отправка, «печатает…», прочтение и поиск незнакомого собеседника
  ограничены таймаутом — по «полуживому» соединению ни HTTP-запрос, ни
  приём сообщений не повиснут.
- Сторож планового тика (`live-account.ts` → `watchdogTick`, с тестами)
  пересоздаёт клиент, если синхронизация зависла, sender мёртв, соединение
  молчит 5 минут или не подключено два тика подряд.
- Фоновая работа процесса (клиенты Telegram, поллер лестницы, приём событий
  агентом, уборка журнала) стартует после `listen` (`common/lifecycle.ts` →
  `whenListening`): экземпляр, которому порт не достался, выходит с кодом 1,
  не тронув сессии Telegram и очередь заданий.
- Новый `send-code` по тому же номеру закрывает клиента прежней попытки входа.
- Сессии в базе только зашифрованные; облачный пароль не хранится.
- При остановке API клиенты аккуратно отключаются без logout — сессии
  остаются действительными.

**Начала диалогов и статистика.** «Начало диалога» — отдельная таблица
`telegram_dialog_starts`: одна строка на диалог, который начал собеседник,
с датой, текстом первого сообщения, распознанным кодом и версией парсера.
Строка создаётся в момент, когда синхронизация узнала первое сообщение
чата (`services/telegram-dialog-starts.service.ts`), и это единственный
источник для вкладки «Статистика»: запрос группирует строки по локальному
дню в зоне `tz` и по `lead_code`, используя индекс `(account_id, started_at)`.
Чаты и сообщения в статистике не участвуют, поэтому она не зависит от их
объёма.

Код распознаётся в `lib/lead-code.ts` по шаблонам «#1», «# 1», «№1»,
«Код 6», «код - 6», «код: 6», «код #6», «code 6», «промокод 6»; всё прочее —
«без кода». Перед разбором текст очищается от невидимых символов (ZWJ, word
joiner — их вставляют в шаблоны против спам-фильтров). Если кодов несколько,
берётся первый по позиции. Текст первого сообщения хранится в таблице, так
что при изменении шаблонов достаточно поднять `LEAD_CODE_PARSER_VERSION`:
строки со старой версией пересчитаются при следующем старте API.

Зависимости идут сверху вниз: контроллеры → сервисы → рантайм и
репозитории → база. Другие модули (realtime, агент) берут из
TelegramModule шину событий, исходящие, рантайм, репозитории и guard'ы;
на события подписываются через `TelegramEventsService.subscribe` — в каждом
событии уже есть `userId` владельца аккаунта.

### Сквозные механизмы

Что контроллер не пишет руками:

- **Раздел выключен.** `TelegramEnabledGuard` на всех контроллерах Telegram
  отвечает 503 с подсказкой, если не заданы `TELEGRAM_API_ID` / `_HASH`, —
  сервисы эту проверку не повторяют.
- **Доступ к аккаунту.** `AccountAccessGuard` на маршрутах с `:id`: проверяет
  формат `:id` (и `:chatId`, если он есть в пути), владение аккаунтом и
  чатом, а найденные строки кладёт в request. Метод берёт их через
  `@Account()` и `@Chat()`, сервисы получают готовые сущности, а не пару
  `userId` + `accountId`.
- **Валидация.** Тела и query-строки — DTO на class-validator под глобальным
  `ValidationPipe` (`whitelist`, `forbidNonWhitelisted`, `transform`):
  лишние поля — 400, числа из query приводятся через `@Type(() => Number)`,
  строки обрезает `@Trim()`. Наружу уходит первая ошибка поля.
- **Ошибки.** `AllExceptionsFilter` не меняет тело `HttpException` (веб читает
  `data.message`), а всё непредвиденное превращает в 500 с одной строкой
  наружу и стеком в логе.

### Как добавить своих пользователей

Ровно так же, как это делает `1700000000001-SeedDemoUser.ts`: создаёте
миграцию и в `up()` пишете `INSERT`. Пароль хешируйте `bcrypt` прямо в
миграции — в репозиторий тогда попадает код, а не готовый хеш:

```ts
const passwordHash = await bcrypt.hash(password, 12);
await queryRunner.query(
  `INSERT INTO "users" ("login", "password_hash", "name") VALUES ($1, $2, $3)`,
  ['ivanov', passwordHash, 'Иванов Иван'],
);
```

Логин кладите в нижнем регистре — поиск идёт по нормализованному значению.

## Переменные окружения

Все — в `.env.example`. При старте `.env` проверяется
(`src/config/env.validation.ts`, class-validator): числа, порты, зона,
уровень логов teleproto, адрес модели, длительность токена. Опечатка роняет
запуск со списком ошибок (только имена переменных, без значений), пустое
значение (`KEY=`) — то же, что не задано. Без `JWT_SECRET` приложение не
стартует.
`CORS_ORIGIN` — список origin'ов через запятую, по умолчанию dev-сервер Vite
на `http://localhost:5173`.

База: `DB_POOL_SIZE` (соединений в пуле, по умолчанию 10),
`DB_STATEMENT_TIMEOUT_MS` (Postgres прерывает запрос дольше этого, 30 000;
миграции идут без ограничения), `DB_SLOW_QUERY_MS` (медленные запросы — в
лог, 1 000). Ожидание соединения из пула ограничено 10 с, брошенная открытой
транзакция закрывается через минуту.

## Заметки по реализации

- Пароли — bcrypt, 12 раундов. При неизвестном логине сравнение всё равно
  выполняется с фиктивным хешем, чтобы по времени ответа нельзя было
  перебирать существующие логины.
- Guard написан на `@nestjs/jwt` без Passport: для одной JWT-стратегии
  Passport даёт мало, а зависимостей и CJS/ESM-стыков добавляет заметно.
- `synchronize` выключен намеренно — схема меняется только миграциями.

## Агент

### Ядро хода (этап 2)

Конвейер одного хода из docs/agent-architecture.md, раздел 3, живёт в
`src/bot/core/` (чистые модули с тестами), `src/bot/services/turn-runner.service.ts`
(оркестрация с базой) и `src/bot/services/turn-llm.service.ts` (обращения к модели):

| Модуль                   | Что делает                                                                                                                                                                                       |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `core/turn-collector.ts` | окно тишины, «печатает», поколения генерации — время получает снаружи                                                                                                                            |
| `core/analysis.ts`       | разбор JSON анализатора: карточка с уверенностью, факты, намерения, риски, пункты для ответа с темой; всё, по чему код решает, — из закрытых списков                                             |
| `core/memory.ts`         | слияние карточки (увереннее побеждает), факты с противоречиями, пороги пола и категории, «липкий» язык                                                                                           |
| `core/plan.ts`           | план хода: передача → веха → ответить → подталкивание → ограничения; таблица вех, темы, которые раскрываются только вехой (`TOPIC_HOLDS`)                                                        |
| `core/writer-output.ts`  | JSON ответчика: `messages` (до вехи), `after_block` (после), мета                                                                                                                                |
| `core/hard-checks.ts`    | синтаксическая страховка: никаких сумм с валютой в тексте ответчика, адреса только из библиотеки, нет служебной разметки, письменность языка, лимит частей, тело вехи побайтно, нарезка под 4096 |
| `core/delivery.ts`       | задержки «как человек» (присутствие, «печатает», паузы) и отправка с остановкой при устаревании                                                                                                  |
| `core/said.ts`           | реестр сказанного по итогу хода: веха (и ссылки), подталкивание, подход к возражению, аргументы; запасная фраза шага воронки не делает                                                           |
| `prompts/*.prompt.ts`    | три промпта, все в JSON-режиме: анализатор (t=0), ответчик (t=0.7), проверяющий (t=0)                                                                                                            |
| `llm/deepseek.client.ts` | DeepSeek через OpenAI-совместимый API, `DEEPSEEK_API_KEY`, `DEEPSEEK_BASE_URL`, `BOT_LLM_TIMEOUT_MS`                                                                                             |

`TurnRunnerService.run(request, { channel, clock, isStale })` выполняет ход
целиком под замком чата: ключ идемпотентности до первой отправки, журнал в
`bot_turns` с промптами в `bot_prompt_snapshots`, память и реестр
сказанного, задания в `bot_jobs`. Канал и часы — интерфейсы из
`core/channel.ts`: их реализуют Telegram-канал и песочница. Библиотека,
память и история читаются параллельно, сбой на любом шаге (в том числе при
чтении) записывается в журнал и ставит повтор.
Ход по расписанию (`trigger: 'schedule'`) пропускает анализ и берёт цель
из задания. После вехи `prices` чат переходит менеджеру с ярлыком
«цены отправлены, молчит».

Смысл текста код не разбирает: о чём вопрос клиента, какой язык, какое
возражение — называет анализатор значениями из закрытых списков, а код
принимает решения по ним. Регулярки остались только там, где проверка
чисто синтаксическая (сумма с валютой, адрес, письменность).

Черновик переписывается только при грубом нарушении (`HARD_CODES`),
стилистические замечания идут в журнал. Повторная проверка — только если
первая нашла выдуманные факты, цены, повторы, запрещённые темы или не тот
язык (`BLOCKING_CODES`); если они остались, вместо текста уходит запасная
фраза из библиотеки, а веха — как есть.

Устойчивость: временная ошибка модели (сеть, 429, 5xx, таймаут
`BOT_LLM_TIMEOUT_MS`, по умолчанию 30 с) повторяется дважды с паузой 2 и
5 с (повторяется только обращение к модели — сбой записи в базу платного
повтора не вызывает); таймаут покрывает и чтение тела ответа. Ответ,
который не разобрался как JSON, запрашивается ещё раз. Если ход
всё же не удался, он повторяется заданием до 30 минут, потом чат уходит
менеджеру с ярлыком «агент недоступен» (раздел «Лестница молчания»).

Ход по расписанию проверяет условие задания в момент срабатывания: если
оно устарело (диагностика уже ушла, данные рождения пришли, этап сменился),
ход закрывается как `skipped` без обращения к модели. «Ходов на этапе»
считаются по истории переписки (`repliesSince`), а не по времени журнала —
одинаково для Telegram, песочницы и скопированного чата.

Полные промпты и ответы модели (`bot_prompt_snapshots`) хранятся 30 дней:
`services/bot-maintenance.service.ts` раз в час удаляет более старые
пачками по индексу `created_at`; журнал ходов (`bot_turns`) остаётся.

### Песочница (этап 3)

Тот же `TurnRunnerService`, что у Telegram, но с другим окружением
(`services/bot-sandbox.service.ts`, SQL — `repositories/bot-sandbox.repository.ts`):

- сессия — виртуальный чат: строка `bot_chat_state` с `sandbox = true` и
  `bot_sandbox_sessions` (миграция `CreateBotSandbox`); переписка —
  `bot_sandbox_messages` (id — число, как telegram_message_id);
- часы виртуальные (`VirtualClock` в `core/channel.ts`): задержки доставки
  не ждутся, а сдвигают время; пауза и «печатает» записываются у сообщения;
- ход и перемотка идут в фоне (модель отвечает секунды), ответ API сразу
  приходит с `running: true`, веб опрашивает сессию; сообщение за клиента
  во время хода делает ход устаревшим — как «клиент дописал» в Telegram;
- копия реального чата: последние 60 сообщений до выбранного, этап — по
  вехам (`core/copied-chat.ts`: исходящее, в котором есть начало тела вехи
  из библиотеки), память — ходом `restore` анализатора по всей копии;
- удаление сессии — `DELETE bot_chat_state` с каскадом на сессию,
  переписку, память, задания и журнал;
- список сессий — один запрос вместе с этапом и числом сообщений, сессия
  целиком (её веб опрашивает во время хода) — параллельными запросами.

Задания песочницы лежат в общей `bot_jobs` с виртуальным временем: поллер
их не берёт (`sandbox = false` в выборке), их выполняет перемотка. Вкладка
в вебе — «Песочница» на странице аккаунта; в переписке — кнопка «В
песочницу» в шапке и иконка у каждого сообщения.

### Лестница молчания (этап 4)

| Модуль                                 | Что делает                                                                                                                                                                                                                                                            |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `core/ladder.ts`                       | `nextLadderStep` — одна следующая ступень из состояния чата: этап, реестр сказанного, прочитано ли последнее сообщение агента, лимит напоминаний. Интервал «случайный» детерминированно (`stableFraction` от чата, вида и точки отсчёта) — пересчёт не сдвигает время |
| `services/bot-ladder.service.ts`       | `reschedule` — ожидающие ступени чата заменяются результатом `nextLadderStep` (под advisory-lock чата, та же ступень на то же время не трогается)                                                                                                                     |
| `services/bot-job-executor.service.ts` | выполнение задания: есть неотвеченные сообщения клиента — ход клиента со ступенью как срочной; `reply` — повтор ответа; иначе ход по расписанию                                                                                                                       |
| `services/bot-scheduler.service.ts`    | поллер: раз в `BOT_SCHEDULER_POLL_MS` забирает созревшие задания боевых чатов (`FOR UPDATE SKIP LOCKED`), до 10 одновременно; зависшие `running` старше 15 мин возвращает в очередь                                                                                   |

Лестница пересчитывается после каждого хода (в том числе пропущенного
как устаревший) и каждого «прочитано»: ответ клиента так снимает дальние
ступени, прочтение меняет «непрочитанное» на следующую ступень этапа.
План хода задания больше не ставит — только лестница.

Ход, который не удался целиком, повторяется заданием с паузой 1, 2, 5,
10, 12 мин (`reply` для ответа клиенту, тот же вид для ступени); после
30 минут сбоев — передача менеджеру «агент недоступен». Повторы
лестница при пересчёте не трогает.

Поллер стартует, когда канал боевых чатов регистрирует себя через
`BotSchedulerService.registerChannels` — это делает Telegram-канал, когда
HTTP-сервер занял порт (при выключенном Telegram поллер не запускается).
При остановке API поллер перестаёт забирать задания. Живая проверка
без Telegram — `scripts/run-ladder.mjs` (канал в памяти, реальные база и
модель).

### Telegram-канал (этап 5)

`services/bot-telegram.service.ts` подписан на шину `TelegramEventsService`:

- **входящее** в чате с `mode = auto` копится сборщиком хода
  (`core/turn-collector.ts`, окно тишины `quietWindowSec`, потолок
  `quietMaxSec`); ход берёт все неотвеченные сообщения из базы
  (`last_handled_message_id`), в том числе оставшиеся от прерванного;
  новое входящее во время хода делает его устаревшим;
- **новый диалог** агент берёт сам, если агент включён на аккаунте и
  диалог начат клиентом после включения (`core/telegram-inbox.ts`);
  переключатель аккаунта — только про новые диалоги, чат, переданный
  руками, работает и без него;
- **«печатает»** продлевает окно тишины; **«прочитано»** пересчитывает
  лестницу;
- **исходящее не от агента** (веб или телефон) в чате агента — передача
  менеджеру «чужое исходящее»; свои исходящие узнаются по id и по тексту,
  который отправляется прямо сейчас;
- в чате у менеджера сообщение клиента ставит ярлык «нужен ответ», ответ
  менеджера его снимает;
- **аккаунт снова в сети** — чаты агента с неотвеченными сообщениями
  получают задание `reply`;
- ручная смена режима чата пересчитывает лестницу.

Отправка агента идёт через `TelegramOutboundService.sendText`, сохраняется
как своё исходящее и публикуется в шину — веб видит её сразу
(`services/bot-telegram-channels.service.ts`: канал живёт один ход, строку
чата читает один раз, владельца аккаунта помнит). Настройки аккаунта
(включён ли агент, тайминги) канал читает без записи и держит 15 с.
