# Архитектура ИИ-агента

Агент ведёт переписку с новым клиентом от лица энергопрактика: отвечает как
человек, поддерживает разговор и шаг за шагом доводит до сообщения с ценами.
После цен чат помечается «у менеджера», дальше отвечает менеджер.

Документ фиксирует решения владельца от 24–25.09.2026 и заменяет прежние
версии. `new-ai-agent.md` описывает другую модель (ранняя передача
менеджеру, воронка после цен) и используется только как источник идей для
библиотеки фраз.

## 0. Три принципа

1. **Код решает «когда и что отправить», LLM решает «как сказать».**
   Порядок вех и шагов воронки, тайминги, тексты диагностик, предложений и
   цен — в коде и библиотеке. Каждый шаг воронки пишется по своей фразе из
   таблиц: LLM подстраивает её под разговор, но смысл, вопрос и длину
   сохраняет и своего не добавляет. Прошлый агент перескакивал этапы и слал
   не те шаблоны именно потому, что выбирал и то и другое сам.
2. **Воронка по таблицам, отдельный ответ — только когда есть на что.** В
   ходе не больше одного шага воронки. Отдельно LLM отвечает только на то,
   чего шаг не закрывает: вопрос, просьбу вне сценария, возражение.
   Присланные данные, «ок», просьбу о раскладе и рассказ о проблеме
   закрывает сам шаг. Подтверждений («всё записал»), рассуждений («это
   важная деталь»), своих вопросов и приписок к вехам агент не пишет; если
   сказать нечего — молчит (решение владельца от 28.09.2026, заменяет
   прежнее «сначала разговор, право поговорить»).
3. **Ничего не выдумывать.** Цены, ссылки, содержание диагностик, факты о
   практике и о клиенте берутся только из библиотеки, образа и памяти.
   Что проверяемо кодом, проверяется кодом; остальное — отдельным
   проверяющим промптом.

## 1. Решения владельца

| Тема | Решение |
|---|---|
| Граница | До цен агент ведёт диалог сам, включая сомнения и вопросы о практиках. После отправки цен чат уходит менеджеру. Напоминаний после цен нет. |
| Передача менеджеру | Агрессия, кризис, просьба позвать человека, вопрос «вы бот?» (не отрицать и не уклоняться), непонятные сообщения, любое медиа от клиента, язык без материалов в библиотеке. |
| Менеджер | Пишет из веба или из Telegram на телефоне. Любое исходящее не от агента переводит чат в режим менеджера. Возврат к агенту — вручную в вебе. |
| Включение | На аккаунте и отдельно в каждом чате. Только диалоги, начатые клиентом после включения на аккаунте. Старые чаты не трогать. |
| Диагностика | Дословно из библиотеки по категории × пол × язык, без вступления и приписок: текст в таблице — законченное сообщение. |
| Сообщения агента | Шаги воронки — по фразам из таблиц, своими словами, но без добавлений. Отдельный ответ — только на вопрос, просьбу вне сценария, возражение. На «ок» и присланные данные без шага — молчание. |
| Первый ответ | Приветствие и одним сообщением: дата рождения, место рождения и сфера вопроса (как в `usually-dialog.md`). |
| Дата рождения | Нужны дата рождения и сфера; место необязательно — его просим только в первом сообщении, вместе с датой (решение 30.09). Клиент ответил, а даты или сферы нет — просим недостающее ещё раз, всего не больше трёх просьб (первое сообщение и ещё две). Написал, что не знает или не даст дату, — дальше без неё. На «ок, сейчас пришлю» не переспрашиваем. Молчит — напоминание, потом диагностика по тому, что известно (сфера названа — по сфере). |
| Сфера и уточнение | Сферу узнаём всегда (решение 30.09): прислал данные без неё — один раз спрашиваем сферу; не назвал и тогда — общая диагностика. Сфера названа, а подкатегория не ясна и у сферы есть уточняющий вопрос в библиотеке (отношения — «Вы состоите в отношениях?», семья — «У вас уже есть дети?») — один раз уточняем; по ответу анализатор выбирает подкатегорию диагностики, без ответа — основная категория сферы. |
| Переходы | Варианты и цены уходят только по реакции клиента: хочет узнать варианты (или откликнулся без вопроса и возражения) — варианты сразу; выбрал вариант, «все», спросил цену, готов или «да, всё понятно» — цены сразу. По времени — только напоминания (решение 28.09). |
| Рекламная метка | «код 12», «код: 12», «#12» в сообщении клиента — идентификатор рекламы: вырезается до всех промптов, агент его не упоминает и не учитывает. |
| Данные клиента | Пол, город, дату рождения, категорию и язык извлекает отдельный промпт с температурой 0. Пол по тексту (окончания о себе, слова о партнёре: «с мужем» → женщина) и по имени — в том числе из профиля Telegram (с 30.09: явно мужское или женское имя; ник и имя «для обоих» не в счёт, слова клиента важнее). При сомнении универсальная диагностика (подтверждено 30.09: у «Отношений» тексты только женские и мужские, без пола уходит универсальная). Имя из профиля — только для пола: в карточку, резюме и обращение к клиенту не идёт. |
| Клиент молчит на знакомстве | После каждого вопроса знакомства (данные, сфера, уточнение) — одно напоминание, затем диагностика по расписанию по тому, что известно (без сферы — общая). |
| Цена раньше времени | Мягко отложить, вести дальше. Цены только после предложения. |
| Молчание | Не больше 3 напоминаний на чат — считаются все: о данных, после диагностики, после вариантов, о непрочитанном. Следующее сообщение только после прочтения предыдущего; сутки не прочитано — одно напоминание и стоп. Лимит кончился — агент ждёт клиента. |
| Очередь сообщений | Несколько сообщений подряд — один ход, ответ на каждое. Ответ пересобирается, если клиент дописал. |
| Режим работы | Круглосуточно, ночных окон и ночных задержек нет. |
| Язык | Определяет LLM, агент отвечает на языке клиента. Нет материалов на языке — менеджер. |
| Модель | DeepSeek `deepseek-chat`. |
| Образ и тексты | Образ практика, библиотека, цены — свои у каждого аккаунта, редактируются в вебе. |
| Не делаем | Медиа от агента, черновики и обучение на правках менеджера, линию «наставничество», обработку правок и удалений сообщений клиентом. |
| Песочница | Обязательна: симуляция в вебе без Telegram, с виртуальным временем, в том числе из копии реального чата. У новой сессии — имя клиента в Telegram (необязательно): по нему, как в живом чате, определяется пол. |

## 2. Модель: разговор и воронка

Агент — это два слоя, которые работают одновременно.

**Воронка** — четыре вехи, которые нужно доставить клиенту по порядку, и
**шаги** между ними. Веха = длинный текст из библиотеки, который код
отправляет дословно, когда выполнены предпосылки и сработал триггер. Шаг =
короткое сообщение по фразе из таблиц (просьба о данных, «займусь
анализом», вопрос-отклик…), которое готовит следующую веху; LLM пишет его
по фразе, подстраивая под разговор. Не больше одного шага за ход.

**Ответы** — всё, чего шаг не закрывает: вопрос клиента, просьба вне
сценария, возражение, рассказ, когда в ходе нет ни шага, ни вехи. Это
работа LLM: коротко, по существу, без своих вопросов.

### 2.0 Воронка целиком (согласовано с владельцем 28.09)

1. **Знакомство.** На первое сообщение — приветствие и одним сообщением
   дата, место рождения и сфера. Нужны дата рождения и сфера, место —
   необязательно (30.09): его больше не просим. Ответил, а даты или сферы
   нет — в ответ просьба о недостающем («Отношения» → «Пришлите дату
   рождения. Вы сейчас состоите в отношениях?»); дата есть, сферы нет —
   вопрос о сфере. Просьб о данных всего не больше трёх: первое сообщение и
   ещё две; написал, что не знает или не даст дату, — дату больше не
   просим; «ок, сейчас пришлю» — ждём, не переспрашиваем. Сфера названа, но
   подкатегория не ясна и у сферы есть уточняющий вопрос — один раз
   уточняем («Вы состоите в отношениях?»), в той же просьбе о данных, если
   она есть. Данные и уточнение получены или просьбы кончились — «Понял
   вас, сделаю анализ и вернусь» и ссылки; без сферы будет общая
   диагностика, без уточнения — основная по сфере. Молчит после вопроса —
   через 60–90 мин после прочтения одно напоминание о нём; молчит и дальше —
   через 45–75 мин после прочтения напоминания диагностика по тому, что
   известно (сфера названа — по сфере; без сферы — общая: «не увидел вашего
   запроса и сделал общий анализ»).
2. **Ожидание.** Диагностика через 45–75 мин после «займусь анализом»
   («ну что там?» после 45 мин — сразу). На вопросы — короткий ответ, на
   «ок» — молчание.
3. **Диагностика** по сфере × пол. Если текст не заканчивается вопросом —
   следом короткий вопрос, рассказать ли, как это проработать. Хочет
   узнать варианты или откликнулся без вопроса и возражения — варианты
   сразу; спрашивает или сомневается — ответ и предложение рассказать о
   вариантах; молчит — напоминание по фразе из таблицы.
4. **Варианты работы** (в конце — «какое направление ближе?»). Выбрал
   вариант, «все», спросил цену, готов, «да, всё понятно» — цены сразу;
   возражение — отработка по плейбуку; вопрос — короткий ответ; молчит —
   напоминание «всё ли понятно по направлениям?».
5. **Цены** — дальше ведёт менеджер.

Напоминаний не больше трёх на чат (раздел 2.4). Веха «видна» клиенту,
если стоит отметка «прочитано» **или** клиент написал после неё
(`seenByClient`): ответить, не прочитав, нельзя.

### 2.1 Вехи

| Веха | Что уходит | Предпосылки | Не раньше | Триггер |
|---|---|---|---|---|
| `links` | шаг «займусь анализом» + ссылки на страницы | вопросов знакомства больше нет (`intakeMove`): дата рождения (или «не знает / не даст») и сфера известны и уточнять нечего (уточнение уже задано), **или** даты или сферы нет, но просьб о данных было уже три (`MAX_DATA_REQUESTS`) | сразу | в том же ходе клиента |
| `diagnostic` | диагностика по категории × пол × язык (категория — подкатегория, а если не ясна — основная категория названной сферы) | `links` отправлены; **или** этап знакомства и ушло напоминание о последнем вопросе (диагностика по тому, что известно) | 45–75 мин после `links` / после прочтения напоминания | таймер; **или** клиент спросил «ну что там?» после минимума — в том же ходе |
| `offer` | описание практик | `diagnostic` видна клиенту | — | ход клиента: хочет узнать варианты (`asks_practice`, `ready`, `chooses_option`, `asks_price`) **или** откликнулся без вопроса и возражения; по времени — никогда |
| `prices` | стоимость | `offer` видно клиенту | — | ход клиента: выбрал вариант, спросил цену, готов **или** ответил без вопроса и возражения («да, всё понятно»); по времени — никогда |

После `prices` — режим менеджера, ярлык «цены отправлены, молчит» до
первого ответа клиента.

Предпосылки и «не раньше» проверяются кодом из базы: `read_at` исходящих
и сообщения клиента после вехи, время отправки прошлой вехи, карточка
клиента. Триггеры: реакция клиента из анализа (в ходе клиента) или таймер
лестницы — только для диагностики.

Вехи уходят без обрамления: тексты в таблицах — законченные сообщения,
диагностика сама начинается с «я вернулся» и обычно заканчивается
вопросом. Тело вехи вставляет код и сверяет побайтно; что-то перед ним
пишется, только если в ходе есть шаг или ответ клиенту. Вопрос клиента,
на который отвечает сама веха («расскажите о практиках» — описание
практик, «сколько стоит» — стоимость), отдельного ответа не получает.

### 2.2 Этап

Этап не хранится отдельно, он равен последней доставленной вехе:
`intake` (ничего) → `links` → `diagnostic` → `offer` → `prices`. Всё, что
раньше называлось «разрешёнными действиями» и «условиями выхода», сведено
в таблицу вех. Код не даёт отправить веху, если предыдущая не доставлена.

### 2.3 Шаги воронки

Шаг — короткое сообщение, которое готовит следующую веху. У каждого шага
своя фраза из таблиц (вид библиотеки): ответчик пишет шаг по ней — тот же
смысл, тот же вопрос, похожая длина; подстроить под разговор можно,
добавлять своё нельзя. Вариантов несколько — берёт один. Нет фразы на
языке клиента — переводит русскую.

| Шаг (`nudge`) | Когда | Фраза из таблиц |
|---|---|---|
| `ask_birth_data` | первый ответ: дата, место и сфера одним сообщением (то, что клиент уже назвал, не спрашиваем; место — только вместе с датой; сфера названа и нужно уточнение — уточняющий вопрос в том же сообщении, в реестр пишутся оба шага); один раз | `greeting` (+ фраза уточнения) |
| `ask_birth_date` | клиент ответил, а даты нет: ещё раз дата (и сфера, если её нет; уточнение — в том же сообщении, если его ещё не задавали); вместе с первой просьбой не больше трёх просьб о данных | `ask_birth_data` (`agent.ask_birth_date`) (+ фраза уточнения) |
| `ask_sphere` | дата есть, сферы нет (в первом ответе — с приветствием); просьбы о данных — не больше трёх | `ask_request` / `sphere` |
| `clarify_request` | сфера названа, подкатегория не ясна, у сферы есть фраза уточнения; один раз (в первом ответе — с приветствием) | `ask_request` / ключ сферы (`relationships`, `family`) |
| `start_analysis` | вместе с вехой `links`, перед ссылками; утверждение — без «хорошо?» | `wait` (без запроса — вариант `no_request`) |
| `birth_data_reminder` | лестница: клиент молчит после просьбы о данных или вопроса о сфере; одно после каждого вопроса, ровно о том, чего не хватает (дата, сфера; место — нет) | `no_birth_data` |
| `clarify_reminder` | лестница: клиент молчит после уточнения; один раз | `ask_request` / ключ сферы |
| `general_analysis` | перед общей диагностикой молчащему клиенту (если диагностика сама заканчивается вопросом); утверждение | первый абзац `links` / `no_request` («не увидел вашего запроса…») |
| `ask_want_options` | после диагностики без вопроса в конце — отдельным сообщением после неё; или ответ на вопрос/сомнение после диагностики — один раз | нет: короткий вопрос «рассказать, как это проработать?» |
| `ask_feedback` | лестница после диагностики; каждый раз — следующий вариант фразы | `return_question` |
| `ask_offer_questions` | лестница после вариантов; каждый раз — следующий вариант | `nudge` / `offer` |
| `unread_reminder` | сутки не прочитано | нет: LLM пишет одно короткое сообщение по диалогу |

Фразы `ask_request` без категории («Расскажите, что у вас случилось?») и
связка `nudge` / `diagnostic_silent` в ходе не используются: рассказ о
проблеме не выпрашиваем, варианты по времени не уходят.

Правила:

- **Один шаг за ход**; шаги знакомства — один раз (просьбы о данных — до
  трёх), напоминания — пока не кончился лимит. Шаг уже был — клиенту только
  отвечают. Исключение — уточнение внутри просьбы о данных: одно
  сообщение, два шага в реестре.
- **Ответ — только на то, чего шаг не закрывает** (раздел 3.4). Ответ
  идёт раньше шага, одним сообщением; шаг — отдельным.
- **Цена раньше времени** — ответ по фразе `price_deflect`, цены не
  называются. **Возражение** — по фразе из плейбука (`objection` по
  категории, при повторе — следующая); фразы нет — коротко и без давления.
- **О себе только из образа.** Вопросы о практике и биографии — по образу
  и разделу «о себе и о работе» библиотеки. Чего там нет, агент не
  выдумывает: отвечает общо.

### 2.4 Лестница молчания

Если клиент прочитал последнее сообщение агента и молчит, агент
напоминает о себе. Каждая ступень — ход по расписанию (раздел 3). Вехи по
времени уходят только две: диагностика после «займусь анализом» и общая
диагностика молчащему клиенту; варианты и цены — только по реакции.

| Этап | Ступень | Через | Что происходит |
|---|---|---|---|
| `intake` | напоминание о вопросе | 60–90 мин после прочтения последнего вопроса знакомства (данные, сфера, уточнение), если после него ещё не напоминали | шаг `birth_data_reminder` или `clarify_reminder` (напоминание) |
| `intake` | диагностика без ответа | 45–75 мин после прочтения напоминания | веха `diagnostic` по тому, что известно (без сферы — универсальная) |
| `links` | диагностика | 45–75 мин после `links`, прочитано или нет | веха `diagnostic` |
| `diagnostic` | вопрос-отклик | первый — 45–75 мин после прочтения, следующие — 12–16 ч | шаг `ask_feedback` (напоминание) |
| `offer` | вопрос по вариантам | 12–16 ч после прочтения | шаг `ask_offer_questions` (напоминание) |
| любой | непрочитанное | 24 ч без прочтения | одно напоминание по диалогу, дальше ступени не ставятся |

Агент промолчал на «ок» — сообщения клиента всё равно обработаны
(`last_handled_message_id`): лестница идёт дальше, а молчание
отсчитывается от последнего сообщения клиента.

Интервалы случайные внутри диапазона. Ступень ставится только когда
предыдущее сообщение агента прочитано; иначе ждёт ступень «непрочитанное».
Напоминаний любого вида не больше трёх на чат (`maxReminders`); вехи в
лимит не входят. После лимита чат остаётся в `auto` без ступеней: если
клиент напишет, разговор продолжается с текущего этапа.

Если план в момент срабатывания отклонил ступень, лестница не ставит ту
же ступень заново на уже наступившее время — расхождение лестницы и плана
не может крутить пустые ходы по кругу.

Ответ клиента отменяет ступени, до которых больше 10 минут, и они ставятся
заново после хода. Ступень, которая созрела или созреет в ближайшие
10 минут, входит в ход клиента как «срочное»: ответ получается один и
связный («как раз закончил смотреть, сейчас пришлю»).

**Как это устроено.** Ступень не «ставится и снимается» по событиям, а
вычисляется: `nextLadderStep` выводит одну следующую ступень из этапа,
реестра сказанного, прочтения последнего сообщения и счётчика напоминаний.
После каждого хода и каждого «прочитано» ожидающие ступени чата
заменяются результатом. Интервал внутри диапазона выбирается
детерминированно от чата и точки отсчёта, поэтому пересчёт без изменений
ничего не сдвигает. Условие ступени ещё раз проверяет план хода в момент
срабатывания: устаревшая закрывается без обращения к модели. Таймер
диагностики после напоминания о данных отсчитывается от напоминания.

Ходы по расписанию — одно сообщение шага или веха без сопровождения:
агент пишет первым, поэтому не благодарит и не отвечает, не утешает, не
ссылается на слова клиента, которых нет в истории. Веха по расписанию
(диагностика, цены) уходит вовсе без обращения к ответчику. Проверяющий
ловит ответ «в пустоту» кодом `answers_nothing`.

## 3. Ход

Ход — единица работы агента. Всё, что агент отправляет, проходит один
конвейер, независимо от того, что его запустило.

### 3.1 Запуск

- **Ход клиента**: входящее сообщение в чате с `mode = auto`.
- **Ход по расписанию**: созрела ступень лестницы молчания или таймер
  вехи `diagnostic`.

Чат впервые попадает к агенту, когда ingest создаёт диалог, начатый
клиентом, на аккаунте с включённым агентом, и время первого сообщения
позже времени включения. Тогда создаётся `bot_chat_state` с `mode = auto`.
Остальные чаты агент не видит, пока их не передали руками. Переключатель
аккаунта означает «брать новые диалоги»: чат, переданный агенту кнопкой в
переписке, агент ведёт и при выключенном переключателе (так тестовый чат
не тянет за собой настоящих клиентов).

### 3.2 Сборка хода клиента

На чат держится окно тишины: входящее запускает или продлевает его на
25–45 с (случайно), событие «печатает» продлевает ещё на 15 с, верхняя
граница 3 мин. Когда окно закрылось, ход = все входящие с момента
последнего сообщения агента, по порядку. Сообщение, пришедшее после
закрытия окна, но до начала генерации, включается в ход.

У чата есть `generation_seq`. Входящее во время генерации увеличивает его;
результат со старым номером выбрасывается, сборка начинается заново. Если
входящее пришло во время доставки многочастного ответа, оставшиеся части
не отправляются, а следующий ход видит в истории то, что уже ушло.

На чат держится **замок**: ход клиента и ход по расписанию не выполняются
одновременно. Ход по расписанию, заставший замок, ждёт и перепроверяет
своё условие после освобождения.

**Рекламная метка.** Реклама добавляет в первое сообщение идентификатор
(«код 12», «код: 12», «#12») и невидимые символы. Всё, что видят промпты
(новые сообщения и история), идёт без них (`core/client-text.ts`,
синтаксически: слово-метка + число); сообщение из одной метки — пометкой
«пришёл по рекламе, без текста». В базе и журнале остаётся исходный текст.

### 3.3 Анализ

Промпт-анализатор, температура 0, JSON. Вход: карточка, активные факты,
резюме, имя клиента в профиле Telegram (`Channel.clientName`; подсказка
для пола), последние 10 сообщений, новый ход. Выход:

| Поле | Содержание |
|---|---|
| `card` | обновления карточки с уверенностью 0–1 по полю; `sphere` — названная клиентом сфера из закрытого списка (отношения, финансы, здоровье, семья, самореализация, будущее, «всё сразу»), `category` — подкатегория, только если ясна; короткий ответ на уточняющий вопрос («да», «нет, расстались») её называет — по подсказкам категорий (`REQUEST_CATEGORIES[].hint`) |
| `facts` | новые факты и противоречия с активными |
| `summary` | обновлённое резюме |
| `language` | язык новых сообщений: код из списка, `other` или `null`, если по ним не понять («ок», эмодзи, дата) |
| `risk` | агрессия, кризис, просьба позвать человека, вопрос «вы бот», непонятно |
| `intents` | несколько из: `asks_price`, `asks_practice`, `asks_about_practitioner`, `asks_diagnostic_status`, `shares_story`, `ready`, `chooses_option` (выбрал вариант или направление, в том числе «все»), `doubts`, `objects`, `smalltalk`, `answers_question`, `silent_ack` |
| `objection` | категория возражения из списка плейбука или `null` |
| `interest` | 0–3 |
| `mood` | спокоен, грустит, тревожится, скептичен, раздражён |
| `answer_points` | из чего состоит ход, по пунктам; один пункт может покрывать несколько сообщений. Вид пункта: `question`, `request`, `objection`, `story`, `emotion`, `data` (дата, место, сфера), `answer` (короткий ответ на наш вопрос), `greeting`, `ack` («ок», «спасибо», стикер), `other`. Тема: `price`, `practice`, `diagnostic`, `practitioner`, `client`, `other` |

**Код не разбирает текст по смыслу.** Всё, по чему принимаются решения
(тема вопроса, язык, намерение, возражение, риск), анализатор называет
значением из закрытого списка; незнакомое значение отбрасывается, а не
угадывается. Регулярки в коде допустимы только для чисто синтаксических
проверок (сумма с валютой, адрес, письменность) — раздел 3.7.

**Язык «липкий».** Первый определённый язык записывается в карточку сразу;
сменить его может только ход, где клиент написал хотя бы 20 букв. «ok 👍»
не переключает диалог на английский и не уводит его к менеджеру. План и
ответчик берут язык из карточки.

Для хода по расписанию анализ пропускается: намерений нет, память
актуальна.

### 3.4 План хода

План собирает код, без LLM. Это главное место, где живёт «умность» в
управляемом виде. План состоит из пяти частей в фиксированном порядке:

1. **Передача.** Если `risk`, медиа, нет материалов на языке — ход
   завершается передачей менеджеру (раздел 5). Дальше не идёт.
2. **Веха.** Если предпосылки, «не раньше» и триггер какой-то вехи
   выполнены (включая срочные ступени), веха входит в план; тело вставит
   код.
3. **Шаг.** Один шаг воронки по таблице 2.3 и его фразы из библиотеки
   (`plan.phrases`). У вех `links` и `offer` по лестнице — свой шаг перед
   ними.
4. **Ответить.** Из `answer_points` в план попадает только то, чего шаг и
   веха не закрывают (`needsOwnAnswer`): приветствие, «ок», данные и
   короткий ответ на наш вопрос — никогда; рассказ и эмоция — только если
   в ходе нет ни шага, ни вехи; просьба о раскладе и «когда будет» — пока
   диагностика не ушла, их закрывает шаг; вопрос, на который отвечает
   веха этого хода, — тоже. Темы, которые раскрываются только вехой
   (`TOPIC_HOLDS`), получают формулу без раскрытия; ранняя цена — фразу
   `price_deflect`. При возражении — фраза плейбука.
5. **Ограничения.** «Уже было, не повторять» из реестра сказанного, язык,
   число сообщений (одно на ответы, одно на шаг), запрет упоминать цены и
   содержание непройденных вех.

Если после этого нет ни шага, ни ответа — ответчик не нужен
(`needsWriter`): уходит веха сама по себе, а без неё агент молчит (только
«прочитано»). Обычный ход — три обращения к модели, веха без сопровождения
и молчание — одно (анализ), ход по расписанию с вехой — ни одного.

Пример плана:

> Ответить коротко, одним сообщением: 1) спросила, где ты живёшь. Шаг
> воронки (отдельным сообщением): скажи, что понял и займёшься анализом.
> Пиши его по фразе из сценария: «Понял вас) Сделаю анализ и вернусь,
> хорошо?..». Сразу после твоих сообщений система отправит «ссылки» — о
> них не пиши. Уже было: просьба о дате и месте рождения. Не упоминать:
> цены, содержание диагностики.

Правила плана лежат в `turn/plan.ts` и покрыты таблицами тестов
«состояние + анализ → план». Это единственное место, которое нужно
править, когда меняется логика воронки.

### 3.5 Текст

Промпт-ответчик, температура 0.5, JSON-режим провайдера — ответ всегда
разбирается, служебное не может утечь клиенту:

```
{ "messages": ["Сейчас живу во Франции, в Шамони 🙂",
               "Понял вас) Сделаю анализ и вернусь, хорошо?"],
  "notes": "ответил, где живу; шаг по фразе wait" }
```

`messages` — сообщения по порядку: ответы, потом шаг. Тело вехи код
ставит после них сам — место задаёт структура, а не маркер в тексте.
`notes` — только в журнал. Правила ответчика: писать только то, что в
плане; шаг — по фразе из сценария; без своих вопросов, подтверждений
полученного, анонсов своих действий, оценок и пересказа слов клиента, без
вступлений и приписок к вехе.

### 3.6 Проверка

Промпт-проверяющий, температура 0, JSON. Получает план, память, ход
клиента и черновик. Возвращает список нарушений по чек-листу:

- каждый пункт «ответить» закрыт (`unanswered_point`);
- шаг воронки есть и сохранил смысл и вопрос фразы (`step_missing`);
- нет вопросов, кроме вопроса шага (`extra_question`);
- нет лишнего: подтверждений полученного, анонсов, оценок и пересказа
  слов клиента, ответов на то, чего нет в плане, вступлений и приписок к
  вехе (`extra_text`); короткое «спасибо» и приветствие — можно;
- нет фактов о клиенте, которых нет в памяти; нет фактов о практике,
  которых нет в образе и разделе «о себе»;
- нет обещаний сроков, нет цен, сумм и ссылок, кроме библиотечных;
- ничего из «не повторять»; ничего из «не упоминать»;
- язык, обращение на «вы», длина и число сообщений в норме;
- текст не выходит за план (`beyond_plan`: второй шаг, продажа,
  пересказ вехи).

Ответчик вызывается второй раз с замечаниями только при грубых
нарушениях (`HARD_CODES`); стиль идёт в журнал и лишнего вызова не стоит.
Повторная проверка — только если первая нашла выдуманные факты, цены,
повторы, запрещённые темы или не тот язык (`BLOCKING_CODES`), и она
отмечает только грубое. Если такое осталось, текст не уходит: шаг уходит
своей фразой из таблиц как есть (если она на языке клиента), веха — сама;
нет ни того, ни другого — короткая нейтральная фраза из библиотеки; ход
помечается в журнале. Ход с ответчиком — три вызова модели, с
переписыванием — четыре-пять.

### 3.7 Жёсткие проверки

Код, без LLM, последняя линия:

- тело вехи берётся из библиотеки побайтно и встаёт после `messages`;
- в тексте ответчика нет ни одной суммы с валютой (цены уходят только
  телом вехи «стоимость»), все адреса — из образа и библиотеки, нет
  служебной разметки (`{{`, ключей JSON); такая часть режется;
- письменность совпадает с языком карточки — только явный промах на
  длинном тексте (русский ответ латиницей), адреса не считаются;
- сообщений ответчика не больше лимита плана: лишние дописываются в
  последнее (в конце обычно шаг с его вопросом — терять его нельзя);
  каждая часть влезает в 4096 символов;
- отправлять нечего — фраза шага или короткая фраза из библиотеки.

### 3.8 Доставка

Агент ведёт себя как человек с телефоном в руке:

- **Присутствие.** После нашего сообщения практик «в чате» около 5 мин и
  отвечает через 10–40 с. Клиент написал спустя 5–60 мин — 1–4 мин.
  Спустя больше часа — 3–12 мин. Новый лид — 60–240 с. Ходы по расписанию
  без задержки: их момент и так случайный.
- **«Прочитано»** ставится один раз, когда окно тишины закрылось, перед
  «печатает».
- **«Печатает»** ~6 символов в секунду, не более 25 с на часть. Веха:
  «печатает» 5–10 с, потом один текст — как вставка из заметок.
- **Части** уходят с паузами 3–10 с, по одной-две темы на часть.
- Все задержки с джиттером, ночью те же.

Перед первой отправкой ход получает ключ идемпотентности
`chat_id + generation_seq` и записывает его в журнал: второй ход с тем же
ключом не начнётся. Прерванный до сборки текста ход (`interrupted`) ключ
отпускает — его повтор должен пройти.

**Точка фиксации.** Когда текст собран и прошёл проверки, ход записывает
в `bot_turns.delivery` части, план задержек, момент первой части и
последнее сообщение чата, которое видел. Дальше ход только доставляется:
каждая ушедшая часть сразу пишется в `bot_turns.sent` (с
`telegram_message_id` — это и список «своих» для страховки от чужих
исходящих), индекс уходящей части — в `delivery.sending`. Прерванный
после фиксации ход (остановка API, сбой отправки) не собирается заново, а
досылается с того же места: до первой части — только остаток паузы;
часть, которую Telegram принял, а мы не успели записать, находится в
истории по тексту и второй раз не уходит. Если после хода в чате
появилось чужое сообщение (клиент дописал, менеджер ответил), досылать
поздно — ход закрывается с тем, что успело уйти, и ушедшее попадает в
реестр сказанного.

### 3.9 Закрытие хода

- память: карточка, факты, резюме из анализа; реестр сказанного —
  доставленная веха, шаг воронки, подход к возражению, ссылки;
- счётчики: `turns_without_nudge`, `reminders_sent`;
- ступени лестницы молчания ставятся заново от текущего этапа;
- журнал получает ход целиком.

## 4. Память о клиенте

Единый объект `Memory`, который анализ обновляет, а план и ответчик читают.

| Слой | Где | Что | Кто пишет |
|---|---|---|---|
| Карточка | `bot_chat_state.card` | имя, пол, дата и место рождения, «даты не будет» (`birthDateDeclined`: не знает / не хочет называть), сфера, категория, язык; уверенность и id сообщения-источника по полю | анализатор |
| Факты | `bot_client_facts` | свободные утверждения: `situation`, `emotion`, `objection`, `biography`, `preference`, `expectation`; источник, уверенность, `active`/`superseded` | анализатор |
| Резюме | `bot_chat_state.summary` | 5–8 предложений: с чем пришёл, что произошло, что обещано, где разговор | анализатор |
| Сказанное | `bot_chat_said` | доставленные вехи, сделанные шаги воронки, использованные подходы к возражениям, ссылки; id сообщения и время | код по результату хода |

Пороги: пол с уверенностью ниже 0.8 и категория ниже 0.7 считаются
неизвестными. Категория диагностики — подкатегория, а если она не ясна —
основная категория названной сферы (`SPHERE_CATEGORY`: финансы → «Финансы»,
отношения → «Отношения в паре», здоровье → «Здоровье», самореализация и
«всё сразу» → универсальная); нет и сферы — универсальная. В промпт идут до 30
активных фактов, свежие первыми. Повторное возражение одной категории
видно по фактам и меняет подход в плане. Что не хранится: сырые сообщения
(они в `telegram_messages`), выводы LLM о характере клиента, всё, что не
подтверждено его словами.

## 5. Передача менеджеру

Единый список причин и кто их обнаруживает:

| Причина | Обнаруживает | Ярлык в вебе |
|---|---|---|
| медиа от клиента | код, по `media_kind` входящего | нужен ответ |
| агрессия, кризис, «позовите человека», «вы бот?», непонятно | анализатор (`risk`) | нужен ответ |
| нет материалов на языке клиента | код, при выборе вехи | нужен ответ |
| ответ клиента после `prices` | код | нужен ответ |
| отправлены `prices`, клиент молчит | код | цены отправлены, молчит |
| чужое исходящее в чате | код, по списку «своих» id (гонка с `sendText` закрывается сверкой текста с очередью ожидающих отправок) | без ярлыка: менеджер уже в чате |
| LLM или Telegram недоступны дольше 30 мин | код | агент недоступен |

При передаче: `mode = manager`, ступени отменяются, в состоянии
сохраняются причина и время. Агент в чате больше не пишет. Любое сообщение
клиента в чате у менеджера ставит ярлык «нужен ответ» (в том числе после
«цены отправлены, молчит»); ответ менеджера — из веба или с телефона —
ярлык снимает; чат остаётся в `manager`.

Режимы чата: `auto`, `manager`, `off`. Переключатели в вебе: на аккаунте
(агент для новых диалогов) и в чате (`auto`/`off`; возврат из `manager` в
`auto` вручную, ступени ставятся заново от текущего этапа). Отправка из
веба — такое же чужое исходящее, как с телефона: чат уходит менеджеру.

## 6. Образ и библиотека

Всё по аккаунту, редактируется в вебе.

**Образ** (`bot_account_settings.persona`): имя, пол, биография (откуда,
где живёт, как пришёл к практике), ссылки на страницы.

**Библиотека** (`bot_library_items`: `kind`, `language`, `gender`,
`category`, `title`, `text`, `sort`):

| Вид | Роль |
|---|---|
| `greeting`, `no_birth_data`, `wait`, `return_question`, `nudge` / `offer`, `price_deflect` | фразы шагов воронки (таблица 2.3): ответчик пишет шаг по фразе — тот же смысл и вопрос, подстроенные под разговор |
| `links` / `no_request` | первый абзац («не увидел вашего запроса…») — шаг перед общей диагностикой молчащему клиенту |
| `ask_request` с категорией | вопросы знакомства: `sphere` — вопрос о сфере, ключ сферы — уточняющий вопрос внутри неё; уточнение задаётся только для сфер, у которых фраза есть (в стандартной библиотеке — отношения и семья), новую сферу владелец добавляет фразой в вебе |
| `ask_birth_data`, `ask_request` без категории, `nudge` / `diagnostic_silent`, `empathy` | в ходе не используются (рассказ о проблеме не выпрашиваем, варианты по времени не уходят, `empathy` — «выбрал комплекс», это уже после цен) |
| `links`, `diagnostic`, `offer`, `prices` | тела вех, уходят дословно |
| `objection` | плейбук возражений: категория `expensive`, `think_about_it`, `dont_believe`, `no_time`, `ask_partner`, `tried_before`, `later`; 2–3 подхода на категорию с порядком при повторе |
| `about` | «о себе и о работе»: вопрос и ответ от лица практика — где живёт, сколько практикует, как проходит чистка, что чувствуют после, чем отличается от психолога; единственный источник фактов о практике |

Выбор диагностики: категория × пол × язык; нет — универсальная для пола и
языка; нет и её — передача менеджеру.

**Примеры** (`bot_examples`: `stage`, `situation`, `client`,
`practitioner`, `enabled`): отобранные вручную обмены из реальной
переписки, 3–5 на этап, добавляются кнопкой «в примеры» в чате с заменой
имён, дат и городов на обобщённые. Идут в промпт ответчика как эталон тона
и длины.

**Тайминги** (`bot_account_settings.timings`): окно тишины, задержки
присутствия, скорость «печатает», интервал `diagnostic`, интервалы
ступеней, лимит напоминаний.

Импорт из `docs/source/*.xlsx` — разовый скрипт при создании аккаунта;
лист «наставничество» и блоки с видео не импортируются.

## 7. Сборка промптов

Порядок частей одинаков во всех промптах и подчинён кэшу префикса
DeepSeek: **статика → история → память → план → новый ход**. Статика
(образ, правила, примеры и библиотека этапа) и старый хвост истории
совпадают с прошлым вызовом и оплачиваются по кэш-тарифу; память и план
меняются каждый ход и стоят в конце, рядом с ходом клиента, где модель
читает внимательнее.

История идёт целиком, до 60 сообщений; старшие обрезаются и остаются
только в резюме. Тела вех в истории заменяются заглушкой
`[отправлена диагностика: отношения, женская]`, медиа клиента —
`[фото]`, `[голосовое]`.

Системные правила поведения общие для всех аккаунтов и живут в коде;
всё, что отличает практика, — в образе и библиотеке.

## 8. Каналы, время, песочница

Ядро не знает, откуда пришли события и куда уходят сообщения:

```ts
interface Inbox   { subscribe(handler: (e: InboxEvent) => void): () => void }
// InboxEvent: message | read | typing — с chatId и телом
interface Channel { send(chat, text): Promise<{ messageId }>; setTyping(chat, on); markRead(chat);
                    history(chat, limit); clientName?(chat): Promise<string | null> }
interface Clock   { now(): Date; sleep(ms): Promise<void> }
```

Telegram: `Inbox` над `TelegramEventsService.subscribe`, `Channel` над
`TelegramOutboundService`, реальные часы. Планировщик (`bot_jobs`,
поллер раз в 30 с) и доставка берут время только из `Clock`.

**Песочница**: `Inbox` — форма в вебе, где владелец пишет за клиента и
жмёт «прочитано»; `Channel` пишет в `bot_sandbox_messages`; `Clock`
виртуальный, кнопка «промотать до следующего события» двигает его к
ближайшей ступени и выполняет её. Задержки доставки показываются числом,
не ждутся. Состояние, память и журнал — те же таблицы, что у боевых чатов,
с `sandbox = true`. У новой сессии владелец задаёт имя клиента в Telegram
(`bot_sandbox_sessions.client_name`, необязательно): `Channel.clientName`
отдаёт его анализатору, как имя собеседника в живом чате; у копии чата это
имя собеседника.

**Из реального чата**: у сообщения в переписке кнопка «продолжить в
песочнице». Копируется история до этого сообщения включительно, память
восстанавливается прогоном анализатора по копии, этап — по последней
доставленной вехе. В исходный чат ничего не пишется.

## 10. Надёжность

- Сбой LLM внутри хода: таймаут вызова 30 с, два повтора с паузой 2 и
  5 с; ответ, который не разобрался как JSON, запрашивается ещё раз. Ход,
  который всё равно не удался, повторяется заданием с нарастающей паузой
  (1, 2, 5, 10, 12 мин) — для человека такая задержка естественна; после
  30 минут сбоев чат уходит менеджеру с ярлыком «агент недоступен».
- Поллер забирает задания через `FOR UPDATE SKIP LOCKED`, ход по заданию
  защищён ключом `job:<id>` — два экземпляра API одно задание не выполнят.
- Остановка API (SIGTERM/SIGINT): новые ходы не начинаются, идущие
  останавливаются в безопасной точке — паузы и обращения к модели
  прерываются, начатая отправка доходит (до 35 с); только потом
  закрываются клиенты Telegram и база. Чужое исходящее и «прочитано»
  обрабатываются, пока живы клиенты.
- Старт после остановки или падения (`BotRecoveryService`, до первого
  хода): ход без точки фиксации помечается `interrupted` и повторяется
  (его задание — снова в очереди, ход клиента — заданием `reply`); ход с
  точкой фиксации досылается заданием `resume`; остальные задания
  `running` сразу возвращаются в очередь; лестница пересчитывается у всех
  чатов под агентом. Новый ход в чате сначала доводит незакрытые прошлые.
- Пропущенное за время офлайна: ходы ждут, пока аккаунт догрузит
  пропущенное (первая синхронизация после подключения), а сообщения и
  прочтения, которые догрузила синхронизация, уходят в шину как живые —
  агент отвечает, берёт новых лидов, замечает ответ менеджера с телефона,
  пересчитывает лестницу. Неотвеченное, что уже было в базе, подхватывает
  задание `reply` при подключении аккаунта.
- Песочница не досылается: её прерванные ходы помечаются `interrupted`,
  ответ повторяется кнопкой.
- Второй инстанс API рядом с боевым запускать только без Telegram
  (иначе Telegram отзывает сессию); ядро при этом работает в песочнице.
- Правки и удаления сообщений клиентом не обрабатываются: ход видит текст
  на момент получения.

## 11. Наблюдаемость

журнал раскрывается под каждым сообщением агента.

   «женщинам»/«мужчинам», поэтому без пола уходила универсальная — анализатор
   получает имя из профиля Telegram (`Channel.clientName`: чат — `peer_name`,
   песочница — имя исходного чата, если она из копии); в карточку имя из
   профиля не попадает (`withoutProfileName`), в резюме — по промпту.
10. **Дата рождения — всегда.** По песочнице владельца от 30.09.
   *Сделано 30.09.2026:* на «Отношения» без даты агент больше не идёт к

   сессии (миграция `BotSandboxClientName`). Сценарии L–O в
